## 1. 배경 및 문제 정의

### 1-1. 현재 상황
- 손님 방문 시 필요한 부품이 없으면 **현대모비스에 주문 → 부품 입고 → 손님께 재연락 → 예약 → 작업** 순서로 진행됨
- 부품이 실제로 입고되었음에도 **엔지니어가 고객에게 연락하는 과정이 반복적으로 누락**되고 있음
- 부품 반품 가능 기한(**입고 후 1개월 이내**)을 넘겨 반품이 불가능해진 재고가 누적되고 있음
- 결과적으로 **사용되지 않는 부품 재고가 계속 쌓이고, 매입 비용이 고스란히 손실로 전환**되는 상황

### 1-2. 핵심 문제
> "부품은 도착했는데, 그 사실이 고객에게 전달되지 않는다"

이 하나의 커뮤니케이션 갭이 반품 기한을 넘기게 만들고, 그대로 재고 손실로 이어짐. 즉 이 시스템의 존재 이유는 **재고관리 자체가 아니라, "입고 후 통보"라는 한 단계가 절대 누락되지 않도록 강제하는 것**임.

## 2. 목표

| 목표 | 설명 |
|---|---|
| 1차 목표 | 부품 입고 후 고객 통보 누락을 0건에 수렴시킨다 |
| 2차 목표 | 반품 기한(1개월) 내 미예약 부품을 조기에 식별해 반품 처리율을 높인다 |
| 3차 목표 | 엔지니어별/지점별 미처리 건을 한눈에 파악할 수 있게 한다 |

| 반품 기한 | 부품 입고일로부터 1개월 |

## 5. 핵심 워크플로우

```
① 고객 방문/접수
      │
② 필요 부품 없음 → 모비스에 부품 주문
      │
③ 부품 입고 → 전산 등록 (입고일 기록됨, 여기서부터 D+0 카운트 시작)
      │
④ 엔지니어에게 "입고 알림" 발송 → 엔지니어가 직접 고객에게 연락
      │
      ├─ 성공: 예약 성사 → 예약 정보 등록 → 종료(정상 플로우)
      │
      └─ 실패 또는 미처리 (D+3까지 예약 미등록)
              │
         ⑤ 1차 통보 (고객에게 문자/카카오톡)
              │
              ├─ D+3~D+7 사이 예약 성사 → 예약 등록 → 종료
              │
              └─ D+7까지 회신 없음
                      │
                 ⑥ 2차 통보 (고객에게 문자/카카오톡)
                      │
                      ├─ D+7~D+14 사이 예약 성사 → 예약 등록 → 종료
                      │
                      └─ D+14까지 회신 없음
                              │
                         ⑦ 최종 통보 (지점 사무실 + 엔지니어 + 고객, "반품 예정" 안내)
                              │
                         ⑧ D+30(반품기한) 임박 시 관리자 화면에 "반품 처리 필요" 표시
```

**핵심 설계 포인트**
- D+3, D+7, D+14는 모두 **입고일(D+0) 기준 자동 카운트**되어야 하며, 사람이 날짜를 계산해서 챙기는 방식이면 안 됨 (현재 문제의 재발 방지가 목적이므로).
- **영업일 기준으로 카운트한다 (토·일 휴무 반영, §11-3 참고)** — 예: 금요일 입고 시 D+3은 화요일(토·일 제외하고 3영업일 후)
- 중간에 예약이 성사되면 **그 시점에서 알림 스케줄이 즉시 중단**되어야 함 (이미 예약 잡은 고객에게 통보 문자가 또 나가면 안 됨).

## 9. 성공 지표 (KPI)

- 부품 입고 후 반품 기한 초과 건수: **월 N건 → 0건 목표**
- 1차 통보 이전에 엔지니어가 자체적으로 예약 성사시키는 비율 (엔지니어 대응력 지표)
- 최종 통보(D+14) 도달 후 실제 반품 처리 완료율
- 손실 규모는 **금액이 아닌 건수 기준으로만 모니터링** (수기 입력 부담을 줄이기 위해 부품 단가 필드는 두지 않기로 확정)

> 목표 수치는 지점 사장님과 협의해서 채워 넣는 걸 추천드려요.

## 11. 확인이 필요한 사항 (Open Questions) — 확정 내역

1. ~~문자/카카오톡 자동 발송을 어떤 채널로 할지~~
   → **확정: 카카오 알림톡(사업자 등록 있음) 우선 발송, 실패 시 SMS/LMS 자동 대체발송**
2. ~~"1차 통보"는 자동 발송인지 수동인지~~
   → **확정: 완전 자동. 입고일(D+0) 기준 D+3까지 예약 미등록 시 시스템이 자동으로 1차 통보 발송**
3. ~~RO번호 체계~~
   → **확정: 지점 기존 전산(GSW 등)에서 쓰이는 RO번호 체계를 그대로 사용. 이 시스템에서 별도 채번하지 않음**
4. ~~엔지니어에게 가는 "입고 알림" 채널~~
   → **확정: 카카오 알림톡(엔지니어 개인 폰) + 시스템 내 대시보드 병행**
   - 사유: 엔지니어가 공용 컴퓨터 앞에 없는 시간이 많아(작업장/차량 밑) 시스템 내 알림만으로는 확인이 누락될 위험이 큼. 개인 폰 알림톡을 1차 트리거로, 시스템 대시보드의 "미처리 건" 목록은 놓쳤을 때의 2차 안전망으로 병행
5. ~~한 RO번호에 부품이 여러 개 묶이는 경우~~
   → **확정(잠정): RO 단위로 묶어서 관리.** 상세는 §11-1 참고, **클라이언트 확인 필요 항목 있음**

### 11-1. RO 단위 관리 방식 — 데이터 모델 메모

한 RO에 부품이 여러 개 걸려있을 때(예: 브레이크 패드 + 오일필터), **입고완료/통보여부/예약여부는 부품 단위가 아니라 RO 단위로 하나만 존재**하는 것으로 설계함.

- **입고완료 시점** = 해당 RO에 걸린 **모든 부품이 도착한 날** (가장 늦게 도착한 부품 기준)
- **D+0(통보 카운트 시작일)** = 위 입고완료 시점
- 화면에는 부품이 여러 줄로 보이더라도, 상태값(입고현황/1차 통보/2차 통보/예약여부)은 RO 전체가 공유

**이렇게 설계한 이유**
- 고객 입장에서 부품별로 여러 번 통보 오는 것보다 "다 모였으니 오세요" 한 번이 자연스러움
- 대부분의 경우 부품이 일부만 와서는 작업 자체가 시작 안 됨(예: 브레이크 패드만 있고 오일필터가 없으면 정비 미완료)

> ⚠️ **클라이언트 확인 필요**: "부품이 부분적으로만 도착해도 그 부분 작업은 먼저 진행 가능한 케이스"가 실제로 있는지 확인 필요. 만약 있다면(예: 브레이크 패드만 와도 그 작업은 먼저 하고 오일필터는 나중에 별도 예약), 현재의 "RO 단위 통합 관리" 모델로는 대응이 안 되고 **"부품 단위 상태 + RO 단위 예약"을 혼합한 모델**로 변경 필요. 이 경우 데이터 구조와 알림 로직 모두 추가 설계가 필요하므로 사전 확인 필수.

### 11-2. 반품 처리 기록 범위 — 클라이언트 확인 필요

- **확정**: 반품 처리는 '완료' 체크만 남긴다 (반품 신청 자체는 GSW 등 기존 전산에서 별도 처리)
- ⚠️ **클라이언트 확인 필요**: 반품 처리 시 **사유·처리자까지 기록해야 하는지** 여부. (현재는 불필요하다고 보고 있으나, 최종 확인 후 확정)

### 11-3. D+3/D+7/D+14 카운트 기준 — 최종 확인 필요

- **잠정 확정**: 토·일 휴무이므로 **영업일 기준**으로 카운트한다 (달력일 기준 아님)
- ⚠️ **최종 확인 필요**: 위 내용이 맞는지 클라이언트 최종 컨펌 요망. (공휴일도 휴무일로 제외할지 여부도 함께 확인하면 좋음 — 예: 설/추석 연휴)

### 11-4. 고객 거절(회신 후 거부) 시 사유 구분 — 클라이언트 확인 필요

- 현재 플로우는 "회신 없음 → 반품"만 정의되어 있고, "회신은 왔으나 고객이 거절"하는 케이스는 별도 상태로 없음
- 이 경우도 결국 반품 처리로 이어지긴 하나, **"미회신으로 인한 반품"과 "고객 거절로 인한 반품"을 사유로 구분해서 기록할지**는 아직 미정
- ⚠️ **클라이언트 확인 필요**: 사유 구분 시 직원 입력 부담이 늘어나는 트레이드오프가 있음 (기존 전산 시스템이 불편해서 잘 안 쓰인다는 배경이 있어, 최대한 간단한 설계를 지향하는 중). **현재는 불필요하다고 보고 있으나, 사장님 확인 후 확정**

### 11-5. 알림톡 발송 가능 시간대 — 확인 필요

- 카카오 정책상 알림톡은 **야간(21시~08시) 발송이 원천 제한**되어 있음 (이 시간대에 트리거되면 다음날 아침으로 자동 이연 필요)
- 지점은 **업무시간(영업시간) 내에만 발송**되길 원함 — 카카오 기본 제한(08~21시)보다 더 좁은 범위로 제한해야 하는지, 아니면 카카오 기본 정책 그대로 따라도 되는지는 미정
- 알림톡 템플릿 문구는 **클라이언트 측에서 작성해서 전달하기로 함** → 전달 시 **카카오 알림톡 템플릿 가이드라인(문구 형식, 변수 처리, 버튼 규칙 등)을 함께 전달 필요**
- ⚠️ **확인 필요**: 지점의 정확한 영업시간(예: 09:00~18:00 등)을 받아서 발송 허용 시간대로 설정
