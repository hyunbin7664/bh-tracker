## 1. 배경 및 문제 정의

### 1-1. 현재 상황
- 손님 방문 시 필요한 부품이 없으면 **현대모비스에 주문 → 부품 입고 → 손님께 재연락 → 예약 → 작업** 순서로 진행됨
- 부품 반품 가능 기한은 모비스 규정상 **입고 후 2개월**이나, 지점은 여유를 두고 자체적으로 **입고 후 30일**을 기준으로 반품 여부를 판단해왔음 (내부 운영 기준, §11-3)
- 부품이 실제로 입고되었음에도 **엔지니어가 고객에게 연락하는 과정이 반복적으로 누락**되어, 이 자체 기준(30일)마저 넘기는 경우가 발생하고 있음
- 결과적으로 **사용되지 않는 부품 재고가 계속 쌓이고, 매입 비용이 고스란히 손실로 전환**되는 상황

### 1-2. 핵심 문제
> "부품은 도착했는데, 그 사실이 고객에게 전달되지 않는다"

이 하나의 커뮤니케이션 갭이 지점 자체 반품 기준(30일)을 넘기게 만들고, 그대로 재고 손실로 이어짐. 즉 이 시스템의 존재 이유는 **재고관리 자체가 아니라, "입고 후 안내"라는 한 단계가 절대 누락되지 않도록 강제하는 것**임.

## 2. 목표

| 목표 | 설명 |
|---|---|
| 1차 목표 | 부품 입고 후 고객 안내 누락을 0건에 수렴시킨다 |
| 2차 목표 | 지점 자체 반품 기준(30일) 내 미예약 부품을 조기에 식별해 반품 처리율을 높인다 |
| 3차 목표 | 엔지니어별/지점별 미처리 건을 한눈에 파악할 수 있게 한다 |

## 3. 대상 사용자

| 역할 | 시스템에서 하는 일 |
|---|---|
| 접수 담당(오피스마스터 등) | 고객 접수, 부품 주문, 부품 입고 등록, 예약 등록 |
| 엔지니어 | 담당 차량 확인, 고객 연락 후 예약 성사 처리 |
| 지점 관리자(사장님) | 전체 현황 모니터링, 안내 미발송 방치 건 확인 |

> 시스템 사용자 다수가 중장년층이므로, UI는 큰 글씨/고대비/최소 클릭 원칙을 따름 (별도 UX 가이드 참고).
> 위 역할 구분은 실제 업무상 하는 일의 차이일 뿐, 로그인 시스템이 구분하는 계정 권한이 아니다 (§11-15 확정, 로그인은 지점 단위 공용 계정).

## 4. 용어 정의

| 용어 | 의미 |
|---|---|
| RO번호 | 접수번호(Repair Order Number) |
| 부품 입고 | 주문한 부품이 지점에 실제로 도착한 것 |
| 차량 입고 | 작업 예정일에 고객이 차량을 가지고 실제로 방문한 것 (노쇼의 반대 개념) |
| 노쇼 | 예약된 작업 예정일(+2일 유예 후)에 차량 입고(방문)가 되지 않은 상태 |
| 안내 (구 1차 통보) | 담당 엔지니어가 고객과 전화 연결이 되지 않았을 때, 엔지니어가 수동으로(버튼 클릭) 고객에게 발송하는 알림(카카오톡/문자). "부품이 입고되었으니 엔지니어에게 연락해서 예약을 잡아달라"는 내용 |
| 안내 재전송 | 안내 발송 후 영업일 3일 이내 예약이 등록되지 않으면, 시스템이 동일한 안내를 자동으로 1회 다시 발송하는 것 |
| 반품 예정 통지 | 안내 재전송 후에도 무응답이거나, 재예약 후 노쇼가 재발했을 때 고객에게 발송하는 "부품을 반품할 예정"이라는 안내 알림. 발송과 동시에 입고 현황이 '반품예정'으로 전환됨 (RO 단위, §11-11) |
| 1차 작업 예정일 | 최초 성사된 예약 일자 |
| 2차 작업 예정일(재예약일) | 1차 작업 예정일에 노쇼가 발생해 다시 잡은 예약 일자. 최대 1회만 존재 (§11-8) |
| 반품 기한 | 지점 자체 기준으로 부품 입고일로부터 30일 (모비스 실제 반품 가능 기한은 2개월, §11-3) |

## 5. 핵심 워크플로우

```
① 고객 방문/접수 → RO 생성 + 필요 부품 목록 등록, 모비스에 즉시 주문 처리 (입고 현황 기본값: '주문중', FR-01)
      │
② 부품 입고 (사무실이 부품별로 개별 수령 등록) → 전산 등록
      │  (RO에 걸린 모든 부품이 도착해야 '입고완료'로 인정, §11-1 참고)
      │
③ 입고완료 즉시 → 엔지니어에게 "입고 알림" 발송 (FR-04)
      │
④ 엔지니어가 고객에게 직접 전화
      │
      ├─ 통화 성공 & 예약 성사 → 1차 작업 예정일 등록 → (⑧로 이동)
      │
      └─ 전화 연결 실패
              │
         ⑤ 엔지니어가 수동으로 안내 발송 (버튼 클릭, 고객에게 카카오톡/문자, FR-06)
              │
              ├─ 영업일 3일 이내 고객이 연락해 예약 등록 → (⑧로 이동)
              │
              └─ 영업일 3일 이내 응답 없음
                      │
                 ⑥ 시스템이 안내 자동 재전송 (1회만, FR-06-2)
                      │
                      ├─ 재전송 후 영업일 3일 이내 예약 등록 → (⑧로 이동)
                      │
                      └─ 재전송 후 영업일 3일도 응답 없음 (잠정, §11-12 클라이언트 확인 필요)
                              │
                         ⑦ 고객에게 "반품 예정 통지" 발송 (FR-07)
                            → RO에 걸린 모든 부품을 반품예정으로 일괄 전환 (RO 단위, §11-11)
                            → 종료
      │
⑧ 유효 작업 예정일(2차 작업 예정일이 있으면 그것, 없으면 1차 작업 예정일) + 2일 경과
      │  → 그 시점에 차량 입고(고객 방문) 여부 확인 (FR-08, 유예기간 기준일은 §11-13 확인 필요)
      │
      ├─ 차량 입고 완료 → 정상 종료 (작업 진행)
      │
      └─ 노쇼 (차량 입고 안 됨)
              │
         ⑨ 담당 엔지니어에게 노쇼 알림 → 재예약 시도
              │
              ├─ 재예약 연락 중 고객과 연락 두절
              │      → 고객에게 "반품 예정 통지" 발송 (FR-09)
              │      → RO 전체 반품예정으로 일괄 전환 → 종료
              │
              └─ 재예약 성사 → 2차 작업 예정일(재예약일) 등록 → (⑧ 재수행, 최대 1회, §11-8)
                      │
                      └─ 2차 작업 예정일 + 2일 경과 후에도 노쇼
                             → 더 이상 재예약 유도 없이 고객에게 "반품 예정 통지" 발송 (FR-09, FR-10)
                             → RO 전체 반품예정으로 일괄 전환 → 종료

[별도 트랙] 사무실 내부 모니터링 (FR-06-1)
  RO가 '입고완료' 상태인데 작업 예정일도 비어있고 안내도 발송된 적 없는 상태가
  방치되면, 사무실이 이를 파악해서 담당 엔지니어에게 직접 고객 연락을 지시한다.
  (고객에게 나가는 자동 문자가 절대 아니며, 순수 사내 알림·에스컬레이션이다)
```

**핵심 설계 포인트**
- 안내는 **엔지니어의 전화 연결 실패를 트리거로 한 수동 발송**이 기본이다 (기존 v0.1 "입고 후 D+3 자동 발송" 방식에서 변경됨).
- 안내가 아예 발송된 적 없는 상태(입고완료 + 작업예정일 없음 + 안내 미발송)가 방치되는 것은 **시스템 자동 발송이 아니라 사무실의 내부 모니터링·에스컬레이션**으로 막는다 (FR-06-1, §11-7 확정). 고객에게 자동으로 나가는 문자는 오직 **안내 재전송**과 **반품 예정 통지** 두 가지뿐이며, 그 외의 "예약하라"는 자동 문자는 절대 발송되지 않는다.
- 안내가 일단 한 번 발송된 뒤에는, 영업일 3일 이내 무응답 시 시스템이 **같은 안내를 자동으로 1회 재전송**한다 (FR-06-2, 신규).
- 재전송 후에도 다시 영업일 3일 무응답이면 반품 예정 통지로 넘어간다 (잠정 설계, §11-12 클라이언트 최종 컨펌 필요).
- 문자 발송 관련 대기기간(3일, 3일)은 **영업일 기준**, 반품 기한(30일)은 **캘린더일(주말 포함) 기준**으로 서로 다르게 카운트한다 (§11-3 확정).
- 중간에 예약이 성사되면 **그 시점에서 알림 스케줄이 즉시 중단**되어야 함 (이미 예약 잡은 고객에게 통보 문자가 또 나가면 안 됨).
- 예약 성사 이후에도 **유효 작업 예정일 + 2일이 지나도록 차량이 입고되지 않으면(노쇼)** 별도 트랙으로 처리되며, 재예약은 1회까지만 자동 추적한다 (§11-8). 1차/2차 작업 예정일은 각각 별도 필드로 저장되어 화면에 둘 다 표시된다.
- "반품 예정 통지"는 발송 트리거(①재전송 후 미예약 장기화, ②재예약 연락두절, ③재예약 노쇼 재발) 중 무엇이든 **동일한 알림·상태 전환 로직**을 공유하며, 항상 **RO 단위로 일괄** 전환된다 (§11-11 확정). 사무실에는 별도의 능동적 알림 없이, 입고 현황이 '반품예정'으로 바뀌는 것으로 갈음한다 (§11-9 확정).
- 반품기한(30일) 임박을 시스템이 자동으로 감지해 강조 표시하거나 상태를 전환하는 기능은 **도입하지 않는다** (구 FR-11/FR-11-1 삭제). 실제 모비스 반품 가능 기한은 2개월이고 30일은 지점의 자체 판단 기준일 뿐이라, 자동화보다는 관리자가 필요 시 목록에서 직접 확인하는 방식으로 충분하다고 판단함. 다만 부품별 실제 입고일은 계속 상세 화면에 표시된다 (§11-10 확정).

> - **부품 입고일(RO 단위)** — RO에 걸린 모든 부품 중 가장 늦게 도착한 날짜, 고객 안내 발송 판단의 기준값

> - **최종 처리 상태** (정상완료 / 반품처리 / 진행중) — 지점 대시보드 집계용
> - **반품 처리 완료 여부** (미처리 / 완료) — 체크 형태로만 관리, RO 단위, 사유·처리자 기록은 미포함 (§11-2 확정)

## 7. 기능 요구사항 (FR)

| ID | 요구사항 |
|---|---|
| FR-01 | 접수 시 RO번호, 차량번호, 고객명, 고객 전화번호, 담당 엔지니어와 함께 필요한 부품(부품번호, 부품명)을 등록할 수 있다. 입고 현황은 접수 즉시 기본값 '주문중'으로 설정된다 (§11-14 확정) |

## 11. 확인이 필요한 사항 (Open Questions) — 확정 내역

1. ~~문자/카카오톡 자동 발송을 어떤 채널로 할지~~

2. ~~"안내"는 자동 발송인지 수동인지~~
   → **확정: 담당 엔지니어와 고객 간 전화 연결이 안 될 때 엔지니어가 수동으로 즉시 발송(FR-06). 이후 무응답 시 시스템이 동일 안내를 1회 자동 재전송(FR-06-2). 안내 자체가 한 번도 안 나간 상태의 방치는 시스템 자동발송이 아니라 사무실 모니터링·에스컬레이션으로 처리(FR-06-1)**
3. ~~RO번호 체계~~
   → **확정: 지점 기존 전산(GSW 등)에서 쓰이는 RO번호 체계를 그대로 사용. 이 시스템에서 별도 채번하지 않음**
4. ~~엔지니어에게 가는 "입고 알림" 채널~~
   → **확정: 카카오 알림톡(엔지니어 개인 폰) + 시스템 내 대시보드 병행**
   - 사유: 엔지니어가 공용 컴퓨터 앞에 없는 시간이 많아(작업장/차량 밑) 시스템 내 알림만으로는 확인이 누락될 위험이 큼. 개인 폰 알림톡을 1차 트리거로, 시스템 대시보드의 "미처리 건" 목록은 놓쳤을 때의 2차 안전망으로 병행
5. ~~한 RO번호에 부품이 여러 개 묶이는 경우~~
   → **확정: RO 단위로 묶어서 관리, 부분 반품/부분 작업 없음** (§11-1)

### 11-1. RO 단위 관리 방식 — 확정

한 RO에 부품이 여러 개 걸려있을 때(예: 브레이크 패드 + 오일필터), **입고완료/안내여부/예약여부는 부품 단위가 아니라 RO 단위로 하나만 존재**한다.

- **입고완료 시점** = 해당 RO에 걸린 **모든 부품이 도착한 날** (가장 늦게 도착한 부품 기준)
- 화면에는 부품이 여러 줄로 보이더라도, 상태값(입고현황/안내여부/예약여부)은 RO 전체가 공유
- **확정**: 부품이 부분적으로만 도착해도 그 부분 작업을 먼저 진행하는 케이스는 없다. 부분 반품도 없다 (클라이언트 확인 완료)

### 11-2. 반품 처리 기록 범위 — 확정

- **확정**: 반품 처리는 '완료' 체크만 남긴다 (반품 신청 자체는 GSW 등 기존 전산에서 별도 처리). 사유·처리자 기록은 불필요

### 11-3. 영업일/캘린더일 카운트 기준 — 확정

- **확정**: 문자(안내/재전송) 발송 대기기간 카운트는 **영업일 기준(월~금)**, 반품 기한(30일)은 **캘린더일 기준(주말 포함)** — 서로 다른 기준을 사용한다
- 참고: 반품 기한(30일)은 모비스 실제 규정(2개월)이 아니라 지점이 자체적으로 정한 내부 운영 기준

### 11-4. 고객 거절(회신 후 거부) 시 사유 구분 — 확정

- **확정**: "미회신으로 인한 반품"과 "고객 거절로 인한 반품"을 사유로 구분해서 기록할 필요 없음

### 11-5. 알림톡 발송 가능 시간대 — 확정

- **확정**: 영업시간 = **월~금, 공휴일 제외, 09:00~18:00**. 이 시간 내에만 알림톡이 발송된다
- 알림톡 템플릿 문구는 **클라이언트 측에서 작성해서 전달하기로 함** → 전달 시 **카카오 알림톡 템플릿 가이드라인(문구 형식, 변수 처리, 버튼 규칙 등)을 함께 전달 필요**

### 11-6. 안내 대기기간 — 확정

- **확정**: 안내 발송 후 예약 유도 대기기간은 영업일 **3일**. 재전송 후 대기기간도 동일하게 3일을 적용한다 (재전송 후 대기기간이 별도로 다르게 필요하다면 §11-12와 함께 재확인)

### 11-7. 안내 미발송 방치 시 처리 방식 — 확정

- **확정**: 엔지니어가 안내를 아예 발송하지 않은 채 방치되는 경우, 시스템이 자동으로 고객에게 문자를 보내지 않는다. 대신 "입고완료 + 작업예정일 없음 + 안내 미발송" 상태를 사무실이 모니터링하다가, 방치가 확인되면 사무실이 담당 엔지니어에게 직접 고객 연락을 지시한다 (FR-06-1)
- **확정**: 안내가 일단 발송된 이후에는, 영업일 3일 무응답 시 시스템이 동일한 안내를 자동으로 1회 재전송한다 (FR-06-2)
- **원칙 확정**: 고객에게 자동으로 발송되는 문자는 "안내 재전송"과 "반품 예정 통지" 두 가지뿐이며, 그 외에 "예약을 하라"는 자동 문자는 절대 발송되지 않는다

### 11-8. 노쇼 이후 재예약 허용 횟수 — 확정

- **확정**: 재예약은 1회까지만 허용한다 (최초 예약 + 재예약 1회 = 총 2회 작업 예정일, 각각 1차/2차 작업 예정일로 별도 저장). 2차 작업 예정일에도 노쇼가 나거나, 재예약을 잡으려는데 고객과 연락이 닿지 않으면 더 이상 재예약을 유도하지 않고 반품 절차로 전환한다
- 클라이언트 확정 사유: "두 번째 예약하고도 안 오거나, 두 번째 예약하려는데 전화를 안 받으면 그건 그냥 안 올 사람"

### 11-9. 노쇼 재발/재예약 무응답 시 사무실 알림 방식 — 확정

- **확정**: 사무실에는 별도의 능동적 알림(카톡/문자)을 보내지 않고, "반품 예정 통지" 발송과 동시에 입고 현황이 '반품예정'으로 바뀌는 것으로 갈음한다. 관리자는 목록 화면 필터링(입고 현황 기준)으로 반품 대상 건을 확인한다

### 11-10. 부품별 입고일 상세 화면 노출 여부 — 확정

- **확정**: 개별 부품의 실제 입고일을 RO 상세 조회 화면에 부품별로 표시한다 (FR-16)

### 11-11. 반품 처리 단위 — 확정

- **확정**: 반품 처리(신청부터 완료 체크까지)는 **무조건 RO 단위**로 이뤄진다. 부품 단위 반품 처리는 없다
- 이에 따라 반품 예정 전환(구 AWAITING_RETURN)과 반품 완료 처리는 항상 RO에 걸린 모든 부품에 대해 일괄로 적용된다 (ERD.md 참고)
- 참고: 부품별 실제 입고일 자체는 계속 개별 관리하되(§11-10), 이는 화면 표시와 이력 확인 용도이며 더 이상 반품 처리 단위나 자동 상태 전환에는 사용되지 않는다

### 11-12. 안내 재전송 후 최종 반품예정 전환 대기기간 — 클라이언트 확인 필요

- **잠정 확정**: 재전송 후 다시 영업일 3일을 기다렸다가, 그래도 무응답이면 반품 예정 통지를 발송하고 반품예정으로 전환한다 (총 대기: 최초 발송 3일 + 재전송 3일)
- ⚠️ **클라이언트 확인 필요**: 위 흐름과 기간이 맞는지 최종 컨펌 요망

### 11-13. 노쇼 유예기간(+2일)의 영업일/캘린더일 기준 — 클라이언트 확인 필요

- 작업 예정일 경과 후 "완료 여부"(차량 입고 여부)를 확인하기까지 2일의 유예기간을 두기로 확정했으나, 이 2일이 **영업일 기준인지 캘린더일 기준인지**는 아직 확인되지 않음
- ⚠️ **클라이언트 확인 필요**: 위 2일의 기준 확정 필요

### 11-14. 접수 시 입고 현황 초기값 — 확정

- **확정**: '미주문' 상태 자체가 불필요함. RO 접수(부품 목록 등록 포함) 즉시 입고 현황이 '주문중'으로 시작한다
- 이에 따라 v0.2까지 있던 "접수 후 별도로 부품 주문 처리를 눌러 미주문→주문중으로 바꾸는" 동작(구 FR-02)은 삭제됨. 접수와 주문 사이의 시간차 자체를 시스템이 별도 상태로 추적하지 않는다

### 11-15. 로그인 방식과 접근 권한 분리 여부 — 확정

- **확정**: 로그인은 직원 개인 계정이 아니라 **지점 단위 공용 계정**이다. 로그인 화면은 지점 선택 드롭다운과 비밀번호 입력만으로 구성되며, 로그인 세션은 로그아웃 전까지 별도 만료 없이 유지된다 (자동 로그아웃 없음)
- **확정**: 위 로그인 모델에서는 "이 사람이 엔지니어인지 관리자인지" 시스템이 구분할 방법이 없으므로, 엔지니어·관리자·접수담당 간 시스템 차원의 접근 권한 분리는 하지 않는다 (NFR-04, FR-12, FR-13 반영)
- **확정**: FR-12/FR-13의 "관리자는 전체", "엔지니어는 본인 담당만"은 접근 제한이 아니라, 공용 컴퓨터에서 여러 직원이 번갈아 쓸 때 담당 엔지니어 드롭다운으로 본인 이름을 선택해 필터링해보는 용도일 뿐이다
- 개인별 계정·권한 분리가 필요해지면 추후 별도 기능으로 확장 가능. 로그인·지점 등록·엔지니어 등록의 상세 요구사항은 별도 공통 PRD 문서에서 다룬다
- ⚠️ **후속 작업 필요**: 여러 지점이 하나의 시스템을 공용으로 쓰게 되면서, 기존 ERD.md/API명세.md의 RepairOrder·Engineer 엔티티에 소속 지점을 나타내는 필드가 빠져있음. 별도 이슈에서 ERD/API명세를 보완해야 함
