| 항목 | 내용 |
|---|---|
| 작성일 | 2026-07-07 |
| 최종 수정일 | 2026-09-04 (노쇼 처리 플로우, 수동 1차 통보 반영) |

---

## 1. 배경 및 문제 정의

### 1-1. 현재 상황
- 손님 방문 시 필요한 부품이 없으면 **현대모비스에 주문 → 부품 입고 → 손님께 재연락 → 예약 → 작업** 순서로 진행됨
- 부품이 실제로 입고되었음에도 **엔지니어가 고객에게 연락하는 과정이 반복적으로 누락**되고 있음
- 부품 반품 가능 기한(**입고 후 1개월 이내**)을 넘겨 반품이 불가능해진 재고가 누적되고 있음
- 결과적으로 **사용되지 않는 부품 재고가 계속 쌓이고, 매입 비용이 고스란히 손실로 전환**되는 상황

### 1-2. 핵심 문제
> "부품은 도착했는데, 그 사실이 고객에게 전달되지 않는다"

이 하나의 커뮤니케이션 갭이 반품 기한을 넘기게 만들고, 그대로 재고 손실로 이어짐. 즉 이 시스템의 존재 이유는 **재고관리 자체가 아니라, "입고 후 통보"라는 한 단계가 절대 누락되지 않도록 강제하는 것**임.

## 2. 목표

| 목표 | 설명 |
|---|---|
| 1차 목표 | 부품 입고 후 고객 통보 누락을 0건에 수렴시킨다 |
| 2차 목표 | 반품 기한(1개월) 내 미예약 부품을 조기에 식별해 반품 처리율을 높인다 |
| 3차 목표 | 엔지니어별/지점별 미처리 건을 한눈에 파악할 수 있게 한다 |

## 3. 대상 사용자

| 역할 | 시스템에서 하는 일 |
|---|---|
| 접수 담당(오피스마스터 등) | 고객 접수, 부품 주문, 부품 입고 등록, 예약 등록 |
| 엔지니어 | 담당 차량 확인, 고객 연락 후 예약 성사 처리 |
| 지점 관리자(사장님) | 전체 현황 모니터링, 반품 임박 건 확인 |

> 시스템 사용자 다수가 중장년층이므로, UI는 큰 글씨/고대비/최소 클릭 원칙을 따름 (별도 UX 가이드 참고).

## 4. 용어 정의

| 용어 | 의미 |
|---|---|
| RO번호 | 접수번호(Repair Order Number) |
| 부품 입고 | 주문한 부품이 지점에 실제로 도착한 것 |
| 차량 입고 | 작업 예정일에 고객이 차량을 가지고 실제로 방문한 것 (노쇼의 반대 개념) |
| 노쇼 | 예약된 작업 예정일에 차량 입고(방문)가 되지 않은 상태 |
| 1차 통보 | 담당 엔지니어가 고객과 전화 연결이 되지 않았을 때, 엔지니어가 수동으로(버튼 클릭) 고객에게 발송하는 안내 알림(카카오톡/문자). "부품이 입고되었으니 엔지니어에게 연락해서 예약을 잡아달라"는 내용 |
| 반품 예정 통지 | 1차 통보 후 일정 기간(잠정 영업일 3일, §11-6 확인 필요) 이내 예약이 등록되지 않거나, 재예약 후 노쇼가 재발했을 때 고객에게 발송하는 "부품을 반품할 예정"이라는 안내 알림. 발송과 동시에 입고 현황이 '반품예정'으로 전환됨 |
| 반품 기한 | 부품 입고일로부터 1개월 |

## 5. 핵심 워크플로우

```
① 고객 방문/접수 → RO 생성 + 필요 부품 목록 등록 (입고 현황 기본값: '미주문', FR-01)
      │
② 필요 부품 없음 → (별도 시점) 모비스에 부품 주문 처리 → 입고 현황 '주문중'으로 변경 (FR-02)
      │  (접수와 부품 주문 처리는 시점이 다른 별개 동작, 부품 정보는 ①에서 이미 등록됨)
      │
③ 부품 입고 (사무실이 부품 수령 등록) → 전산 등록
      │  (RO에 걸린 모든 부품이 도착해야 '입고완료'로 인정, §11-1 참고)
      │
④ 입고완료 즉시 → 엔지니어에게 "입고 알림" 발송 (FR-04)
      │
⑤ 엔지니어가 고객에게 직접 전화
      │
      ├─ 통화 성공 & 예약 성사 → 작업 예정일 등록 → (⑦로 이동)
      │
      └─ 전화 연결 실패
              │
         ⑥ 엔지니어가 수동으로 1차 통보 발송 (버튼 클릭, 고객에게 카카오톡/문자, FR-06)
              │
              ├─ 영업일 기준 3일(잠정, §11-6) 이내 고객이 연락해 예약 등록 → (⑦로 이동)
              │
              └─ 3일 이내 응답 없음
                      │
                 ⑦' 고객에게 "반품 예정 통지" 발송 (FR-07)
                    → 입고 현황 '반품예정'으로 전환 → 종료
      │
⑦ 작업 예정일 도래 → 차량 입고(고객 방문) 여부 확인
      │
      ├─ 차량 입고 완료 → 정상 종료 (작업 진행)
      │
      └─ 노쇼 (차량 입고 안 됨)
              │
         ⑧ 담당 엔지니어에게 노쇼 알림 (FR-08) → 재예약 시도
              │
              ├─ 재예약 연락 중 고객과 연락 두절
              │      → 고객에게 "반품 예정 통지" 재발송 (FR-09)
              │      → 입고 현황 '반품예정'으로 전환 → 종료
              │
              └─ 재예약 성사 → 새 작업 예정일 등록 → (⑦ 재수행, 2회차)
                      │
                      └─ 2회차 작업 예정일에도 노쇼 (§11-8: 재예약은 1회로 제한, 확정)
                             → 고객에게 "반품 예정 통지" 재발송 (FR-09)
                             → 입고 현황 '반품예정'으로 전환 → 종료
      │
⑨ D+30(반품기한) 임박 시 관리자 화면에 "반품 처리 필요" 표시 (FR-11)
```

**핵심 설계 포인트**
- 1차 통보는 **엔지니어의 전화 연결 실패를 트리거로 한 수동 발송**이 기본이다 (기존 "입고 후 D+3 자동 발송" 방식에서 변경됨). 엔지니어가 발송을 누락할 경우를 대비해 **입고일 기준 영업일 3일 경과 시 자동 발송되는 안전망**을 잠정 병행한다 (FR-06-1, §11-7 최종 확인 필요).
- 1차 통보 이후의 예약 유도 대기기간(영업일 3일)은 **영업일 기준으로 카운트한다 (토·일 휴무 반영, §11-3 참고)**.
- 중간에 예약이 성사되면 **그 시점에서 알림 스케줄이 즉시 중단**되어야 함 (이미 예약 잡은 고객에게 통보 문자가 또 나가면 안 됨).
- 예약 성사 이후에도 **작업 예정일에 실제로 차량이 입고되지 않으면(노쇼)** 별도 트랙으로 처리되며, 재예약은 1회까지만 자동 추적한다 (§11-8).
- "반품 예정 통지"는 발송 트리거(①미예약 장기화, ②재예약 연락두절, ③재예약 노쇼 재발) 중 무엇이든 **동일한 알림·상태 전환 로직**을 공유한다. 사무실에는 별도의 능동적 알림 없이, 입고 현황이 '반품예정'으로 바뀌는 것으로 갈음한다 (§11-9 확인 필요).
- 반품기한(30일) 임박도 ④번째 트리거로 '반품예정' 상태에 들어가지만, 이건 고객 응대와 무관한 순수 날짜 기반 트리거라 **그 부품 하나만** 개별 전환된다 (①②③은 RO 전체 일괄 전환). 이미 유효한 작업 예정일이 있으면 목록엔 '진행중'으로 계속 보이되 빨간 행으로 경고만 표시된다 (FR-11-1, §11-13 확인 필요).

> **추가 제안 필드** (요구사항엔 없었지만 워크플로우상 반드시 필요해 보임)

## 7. 기능 요구사항 (FR)

| ID | 요구사항 |
|---|---|
| FR-01 | 접수 시 RO번호, 차량번호, 고객명, 고객 전화번호, 담당 엔지니어와 함께 필요한 부품(부품번호, 부품명)을 등록할 수 있다. 입고 현황은 기본값 '미주문'으로 설정된다 |
| FR-02 | 접수 이후 별도 시점에, 등록된 부품을 실제로 모비스에 주문 처리하면(부품 정보 재입력 없이) 입고 현황을 '미주문'에서 '주문중'으로 변경할 수 있다 (접수와 부품 주문 처리는 서로 다른 시점에 일어나는 별개 동작) |
| FR-03 | 부품 입고 등록 시 입고일이 자동으로 오늘 날짜로 기록되고, 입고 현황이 '입고완료'로 변경된다 (RO에 걸린 모든 부품이 도착해야 완료로 인정, §11-1) |
| FR-04 | 입고 등록 즉시 담당 엔지니어에게 카카오 알림톡(개인 폰)이 발송되고, 시스템 내 대시보드에도 미처리 건으로 표시된다 |
| FR-05 | 예약 성사 시 작업 예정일을 등록하면 예약 여부가 '예약완료'로 바뀌고, 이후 1차 통보/반품 예정 통지가 중단된다 |
| FR-06 | 담당 엔지니어와 고객 간 **전화 연결이 되지 않으면**, 엔지니어가 **수동으로** 1차 통보(카카오 알림톡, 실패 시 SMS 대체)를 즉시 발송할 수 있다. 발송 시 1차 통보 여부가 '발송완료'로 표시된다 |
| FR-06-1 | (잠정, §11-7 클라이언트 확인 필요) 부품 입고일 기준 **영업일 3일**이 지나도 예약이 등록되지 않았고 1차 통보도 수동 발송되지 않았으면, 시스템이 자동으로 1차 통보를 발송한다 (엔지니어의 수동 발송 누락 방지 안전망) |
| FR-07 | 1차 통보 발송 후 **영업일 기준 3일**(잠정, §11-6 확인 필요) 이내 예약이 등록되지 않으면 고객에게 "반품 예정 통지"가 자동 발송되고, 입고 현황이 '반품예정'으로 변경된다 |
| FR-08 | 예약이 등록된 작업 예정일이 지났음에도 **차량 입고가 등록되지 않으면(노쇼)** 담당 엔지니어에게 알림이 발송된다 |
| FR-09 | 노쇼 알림을 받은 엔지니어가 재예약 연락 중 고객과 연락이 닿지 않거나, 재예약한 작업 예정일에도 노쇼가 재발하면 고객에게 "반품 예정 통지"가 발송되고 입고 현황이 '반품예정'으로 변경된다 |
| FR-10 | 재예약은 최대 1회까지만 허용하며(재예약 여부 필드), 2회차 작업 예정일에도 노쇼가 발생하면 더 이상의 재예약 유도 없이 FR-09에 따라 반품 절차로 전환된다 (§11-8) |
| FR-11 | 입고일 기준 D+30(반품기한) 임박 건은 관리자 화면 상단에 별도로 강조 표시된다 |
| FR-11-1 | (잠정, §11-13 확인 필요) 부품 입고일 기준 반품기한(30일)이 임박(D-N일 전, N 미정)하면 배치가 해당 부품의 `Part.status`를 `AWAITING_RETURN`으로 자동 전환한다(①안내 무응답 ②재예약 연락두절 ③재예약 노쇼 재발에 이은 4번째 트리거). 단, 그 RO에 아직 지나지 않은 작업 예정일이 있으면 목록 화면상 '진행중' 탭에 그대로 두되, `AWAITING_RETURN`인 건은 탭과 무관하게 행을 빨간색으로 강조 표시한다 |
| FR-12 | 지점 관리자는 전체 건 목록을 입고 현황/예약 여부/담당 엔지니어별로 필터링해서 볼 수 있다 |
| FR-13 | 엔지니어는 본인 담당 건만 필터링해서 볼 수 있다 |
| FR-14 | 관리자(또는 접수 담당)는 반품 처리가 완료된 건에 대해 '반품 처리 완료' 체크를 남길 수 있다 (사유·처리자 기록 없이 완료 여부만) |
| FR-15 | 예약 등록은 누가 입력했는지 구분하지 않으며, 작업 예정일 필드에 값이 있는지 여부만으로 '예약완료' 상태를 판단한다 (엔지니어·접수담당 입력 권한을 분리하지 않음) |

   - 사유: 엔지니어가 공용 컴퓨터 앞에 없는 시간이 많아(작업장/차량 밑) 시스템 내 알림만으로는 확인이 누락될 위험이 큼. 개인 폰 알림톡을 1차 트리거로, 시스템 대시보드의 "미처리 건" 목록은 놓쳤을 때의 2차 안전망으로 병행
5. ~~한 RO번호에 부품이 여러 개 묶이는 경우~~
   → **확정(잠정): RO 단위로 묶어서 관리.** 상세는 §11-1 참고, **클라이언트 확인 필요 항목 있음**

### 11-1. RO 단위 관리 방식 — 데이터 모델 메모

한 RO에 부품이 여러 개 걸려있을 때(예: 브레이크 패드 + 오일필터), **입고완료/통보여부/예약여부는 부품 단위가 아니라 RO 단위로 하나만 존재**하는 것으로 설계함.

- **입고완료 시점** = 해당 RO에 걸린 **모든 부품이 도착한 날** (가장 늦게 도착한 부품 기준)
- **D+0(통보 카운트 시작일)** = 위 입고완료 시점
- 화면에는 부품이 여러 줄로 보이더라도, 상태값(입고현황/1차 통보/예약여부)은 RO 전체가 공유

**이렇게 설계한 이유**
- 고객 입장에서 부품별로 여러 번 통보 오는 것보다 "다 모였으니 오세요" 한 번이 자연스러움
- 대부분의 경우 부품이 일부만 와서는 작업 자체가 시작 안 됨(예: 브레이크 패드만 있고 오일필터가 없으면 정비 미완료)

> ⚠️ **클라이언트 확인 필요**: "부품이 부분적으로만 도착해도 그 부분 작업은 먼저 진행 가능한 케이스"가 실제로 있는지 확인 필요. 만약 있다면(예: 브레이크 패드만 와도 그 작업은 먼저 하고 오일필터는 나중에 별도 예약), 현재의 "RO 단위 통합 관리" 모델로는 대응이 안 되고 **"부품 단위 상태 + RO 단위 예약"을 혼합한 모델**로 변경 필요. 이 경우 데이터 구조와 알림 로직 모두 추가 설계가 필요하므로 사전 확인 필수.

### 11-2. 반품 처리 기록 범위 — 클라이언트 확인 필요

- **확정**: 반품 처리는 '완료' 체크만 남긴다 (반품 신청 자체는 GSW 등 기존 전산에서 별도 처리)
- ⚠️ **클라이언트 확인 필요**: 반품 처리 시 **사유·처리자까지 기록해야 하는지** 여부. (현재는 불필요하다고 보고 있으나, 최종 확인 후 확정)

### 11-3. 영업일 카운트 기준 (1차 통보 대기기간·반품기한) — 최종 확인 필요

- **잠정 확정**: 토·일 휴무이므로 **영업일 기준**으로 카운트한다 (달력일 기준 아님)
- ⚠️ **최종 확인 필요**: 위 내용이 맞는지 클라이언트 최종 컨펌 요망. (공휴일도 휴무일로 제외할지 여부도 함께 확인하면 좋음 — 예: 설/추석 연휴)

### 11-4. 고객 거절(회신 후 거부) 시 사유 구분 — 클라이언트 확인 필요

- 현재 플로우는 "회신 없음 → 반품"만 정의되어 있고, "회신은 왔으나 고객이 거절"하는 케이스는 별도 상태로 없음
- 이 경우도 결국 반품 처리로 이어지긴 하나, **"미회신으로 인한 반품"과 "고객 거절로 인한 반품"을 사유로 구분해서 기록할지**는 아직 미정
- ⚠️ **클라이언트 확인 필요**: 사유 구분 시 직원 입력 부담이 늘어나는 트레이드오프가 있음 (기존 전산 시스템이 불편해서 잘 안 쓰인다는 배경이 있어, 최대한 간단한 설계를 지향하는 중). **현재는 불필요하다고 보고 있으나, 사장님 확인 후 확정**

### 11-5. 알림톡 발송 가능 시간대 — 확인 필요

- 카카오 정책상 알림톡은 **야간(21시~08시) 발송이 원천 제한**되어 있음 (이 시간대에 트리거되면 다음날 아침으로 자동 이연 필요)
- 지점은 **업무시간(영업시간) 내에만 발송**되길 원함 — 카카오 기본 제한(08~21시)보다 더 좁은 범위로 제한해야 하는지, 아니면 카카오 기본 정책 그대로 따라도 되는지는 미정
- 알림톡 템플릿 문구는 **클라이언트 측에서 작성해서 전달하기로 함** → 전달 시 **카카오 알림톡 템플릿 가이드라인(문구 형식, 변수 처리, 버튼 규칙 등)을 함께 전달 필요**
- ⚠️ **확인 필요**: 지점의 정확한 영업시간(예: 09:00~18:00 등)을 받아서 발송 허용 시간대로 설정

### 11-6. 1차 통보 후 재예약 유도 대기기간 — 클라이언트 확인 필요

- **잠정 확정**: 영업일 기준 **3일**
- ⚠️ **클라이언트 확인 필요**: 위 3일이 실제 현장 운영에 맞는지 최종 컨펌 요망

### 11-7. 1차 통보 자동 발송 안전망 병행 여부 — 클라이언트 확인 필요

- **확정**: 1차 통보는 원칙적으로 **담당 엔지니어가 고객과 전화 연결이 안 될 때 수동 버튼으로 즉시 발송**한다 (기존 "입고 후 D+3 자동 발송" 방식에서 변경됨)
- **잠정 확정**: 엔지니어가 수동 발송을 깜빡하는 경우를 대비해, 입고일 기준 영업일 3일이 지나도 수동 발송이 안 됐으면 시스템이 자동으로도 1차 통보를 발송하는 안전망을 병행한다
- ⚠️ **클라이언트 확인 필요**: 이 자동 안전망이 실제로 필요한지, 필요하다면 3영업일이라는 기준일이 맞는지 최종 컨펌 요망

### 11-8. 노쇼 이후 재예약 허용 횟수

- **확정**: 재예약은 1회까지만 허용한다 (최초 예약 + 재예약 1회 = 총 2회 작업 예정일). 재예약(2회차)에서도 노쇼가 나거나, 재예약을 잡으려는데 고객과 연락이 닿지 않으면 더 이상 재예약을 유도하지 않고 반품 절차로 전환한다.
- 클라이언트 확정 사유: "두 번째 예약하고도 안 오거나, 두 번째 예약하려는데 전화를 안 받으면 그건 그냥 안 올 사람"

### 11-9. 노쇼 재발/재예약 무응답 시 사무실 알림 방식 — 클라이언트 확인 필요

- **잠정 확정**: 사무실에는 별도의 능동적 알림(카톡/문자)을 보내지 않고, "반품 예정 통지" 발송과 동시에 입고 현황이 '반품예정'으로 바뀌는 것으로 갈음한다. 관리자는 §9 화면 필터링(입고 현황 기준)으로 반품 대상 건을 확인한다
- ⚠️ **클라이언트 확인 필요**: 최초 요구사항엔 "사무실에 통보"라고 명시되어 있었는데, 상태 변경(대시보드 노출)만으로 충분한지, 아니면 사무실 담당자에게도 별도 알림이 능동적으로 발송되어야 하는지 확인 필요

### 11-10. 부품별 입고일 상세 화면 노출 여부 — 클라이언트 확인 필요

- 개별 부품의 실제 입고일(`Part.received_date`)은 반품 기한 계산(§ERD 참고)을 위해 시스템 내부적으로는 반드시 필요한 값
- ⚠️ **클라이언트 확인 필요**: 이 개별 입고일을 RO 상세 조회 화면에도 부품별로 표시해줘야 하는지, 아니면 내부 계산용으로만 두고 화면에는 노출하지 않아도 되는지 확인 필요

### 11-11. 반품 처리 단위 — RO 단위 vs 부품 단위 — 클라이언트 확인 필요

- FR-14는 "반품 처리가 완료된 **건**에 대해 체크를 남길 수 있다"고만 되어있어 "건"이 RO를 뜻하는지 개별 부품을 뜻하는지 원문 자체가 불명확함
- 반품 기한(입고일+30일) 계산은 부품마다 실제 도착일이 달라서 부품 단위로 추적하는 게 맞다고 판단해 ERD/API를 그렇게 설계해뒀지만(§ERD "RO 레벨 vs Part 레벨"), **실제로 모비스에 반품을 신청하는 물리적 처리 자체가 RO 단위(한 RO에 걸린 부품을 한 번에 묶어서 반품)인지, 부품마다 따로 신청하는지**는 아직 클라이언트에게 확인받지 않음
- ⚠️ **클라이언트 확인 필요**: 반품 신청/처리가 실제 현장에서 RO 단위로 이뤄지는지, 부품 단위로 이뤄지는지. 답변에 따라 FR-14의 체크 단위(RO 전체 일괄 vs 부품별 개별)와 관련 화면·API 설계가 달라짐
- 참고: 반품 기한 임박 여부 자체는 처리 단위와 무관하게 부품마다 개별 계산되어야 함(§9 KPI 목적상 "어쨌든 반품이 필요한 상태"인지 판단하는 기준은 항상 부품의 실제 도착일 기준) — 이 부분은 처리 단위와 별개로 확정된 사항

### 11-12. FR-11(반품기한 임박 강조 표시) 화면 위치 — 화면 설계 시 반영 필요

- FR-11-1에 따라 반품기한 임박 여부는 배치가 `Part.status=AWAITING_RETURN`으로 이미 전환해두므로, 화면은 이 상태값만 보고 빨간 행으로 표시하면 됨 (별도 날짜 계산 불필요, API명세.md 참고)
- 다만 "관리자 화면 **상단**에 강조 표시"(FR-11 원문)를 목록 안에서 빨간 행으로 섞어 보여주는 것으로 충분한지, 아니면 상단에 별도 요약 섹션을 또 둬야 하는지는 와이어프레임 작업 시 결정 필요

### 11-13. 반품기한 임박 판단 기준일(D-N) — 클라이언트 확인 필요

- FR-11-1에서 "반품기한 임박"이 정확히 며칠 전부터인지(D-3? D-7?) 아직 숫자가 정해지지 않음
- ⚠️ **클라이언트 확인 필요**: 반품기한(입고 후 30일) 중 며칠 전부터 `AWAITING_RETURN`(빨간 강조)으로 표시할지 확정 필요
